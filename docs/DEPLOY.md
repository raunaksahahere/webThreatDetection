# Deploying: Render (API, Docker) + Vercel (dashboard)

The API is a long-running service: it starts an isolated inspector process per analysis, keeps SQLite, and talks to a chain. That is why it runs on **Render as a Docker web service**, while the static dashboard can run on **Vercel**. The Render service also serves the dashboard on its own URL, so Vercel is optional.

```
 Vercel (static dashboard, VITE_API_BASE=https://<api>.onrender.com)
      │  HTTPS, X-WTD-Token header, CORS allowed only for the Vercel origin
      ▼
 Render web service (Dockerfile): FastAPI + isolated inspector + SQLite + embedded anvil chain
      └─► Internet (only validated public addresses; cloud metadata and private ranges are blocked by the request boundary)
```

## 1. API on Render
1. Push the repo to GitHub (already done) and, in Render, choose **New → Blueprint** and select the repository. Render reads `render.yaml`.
2. Fill the environment values Render asks for:
   - `WTD_CORS_ORIGINS`: your Vercel URL, for example `https://wtd-dashboard.vercel.app`. You can add it after step 2 of the Vercel part.
   - `GEMINI_API_KEY`: your Google AI Studio key. It powers the AI explanations and campaign briefs. `WTD_GEMINI_MODELS` (set in `render.yaml` to `gemini-3.5-flash-lite,gemini-3.1-flash-lite`) is tried in order, and a model that hits its free daily quota hands over to the next, so the two give about 1,000 explanations a day. If a model id has a suffix such as `-preview`, the API's model list is used to find it. On the free tier Google may use requests to improve its products; the model only ever sees the deterministic findings and redacted message text. After deploying, `/api/health` shows `"ai": {"provider": "gemini", ...}`.
   - `OPENROUTER_API_KEY`: optional second provider. Only `:free` models are accepted by the code. With neither key, reports say "AI unavailable" (there is no local Ollama on Render).
   - `URLHAUS_AUTH_KEY`: optional. Without it, a visitor (for example a judge) can paste their own free abuse.ch key: click the **urlhaus** pill in the header. The key stays in their browser tab (sessionStorage), is sent with each analysis as `X-URLhaus-Key`, takes precedence over the server key, and is never saved on the server or written into a report. `WTD_CORS_ORIGINS` deployments allow this header.
   - `WTD_PUBLIC_DEMO` is `1` in `render.yaml`: anyone with the link can use every feature without the token (for judging). Each browser session gets `WTD_PUBLIC_SESSION_LIMIT` analyses (15), and each visitor address `WTD_PUBLIC_DAILY_LIMIT` per UTC day (60), on top of the per-minute limit. Entering the operator token lifts those limits. On the embedded chain anyone can register, verify and review; on a public chain (Sepolia) those actions still need the token. History is shared between visitors and the dashboard shows a "public demo" banner. Set it to `0` after judging to require the token again.
   - `WTD_API_TOKEN` and `WTD_HMAC_KEY` are generated by Render. Copy `WTD_API_TOKEN` from the service's Environment tab; the dashboard asks for it.
3. Deploy, then open `https://<service>.onrender.com/api/health`. It should report `chain.connected: true`. The CERT Polska list downloads in the background after start (about 2.5 MB from a slow host, so allow a few minutes).

Notes for the free plan:
- The instance sleeps after about 15 minutes idle, and the first request takes roughly a minute to wake it.
- The filesystem is **ephemeral**. Reports and the embedded chain reset on every restart or redeploy. For a demo, run the analyses shortly before presenting. The commented `disk:` block in `render.yaml` (paid plan) keeps `/app/data`.
- The embedded chain is a private anvil instance inside the container, so registrations are not publicly visible. For publicly checkable registrations, deploy to Sepolia with `scripts/testnet.sh`, commit `deployments/sepolia.json`, and switch to the commented `WTD_CHAIN=external` block, giving `WTD_REPORTER_KEY` and `WTD_REVIEWER_KEY` as secrets.
- 512 MB RAM is enough for the API, the per-analysis inspector process and anvil. Analyses run three at a time.

## 2. Dashboard on Vercel
1. In Vercel: **Add New → Project** → import the repository → set **Root Directory** to `frontend`. Vercel reads `frontend/vercel.json` (Vite, `npm run build`, output `dist`, security headers).
2. Add the environment variable `VITE_API_BASE` = `https://<service>.onrender.com` (https, no trailing slash) for Production, then deploy.
   - It is baked in at build time, so redeploy after changing it.
   - The build adds that origin, and only that origin, to the page's Content-Security-Policy `connect-src`.
3. Put the resulting Vercel URL into `WTD_CORS_ORIGINS` on Render (step 1.2). Render restarts the service.
4. Open the Vercel URL and paste the operator token when asked. It is kept in that browser tab only (sessionStorage).

## 3. Local Docker (same image)
```bash
docker build -t wtd .
docker run --rm -p 8000:8000 -e WTD_API_TOKEN=change-me wtd      # http://127.0.0.1:8000/
```

## Security notes for a public instance
- Every route except `/api/health` and the static dashboard needs the operator token. Use the generated value and do not share it publicly. Rotate it in Render to revoke access.
- Rate limits are per client address: 12 analyses per minute, and 300 quick checks per minute. The container trusts Render's forwarded client address.
- Submitted URLs are fetched by the server. The request boundary blocks private, loopback, link-local/metadata and IPv6-embedded addresses, re-validates every redirect, and connects only to validated IPs. On a cloud host, this is what keeps the instance from being used to reach internal services.
- The companion extension is pinned to `http://127.0.0.1:8000`; it is for local use and is not affected by this deployment.
